This change is local source preparation, not a deployment. Tests use isolated synthetic records. Planner mathematics, priorities, policies, API contracts and Cognito/PKCE remain unchanged.

Startup/auth handles Cognito tokens, PKCE and subject identity; api attaches the existing identity token and reports session expiry. Operations submits versioned events and approval requests. The local operation store and cloud handler already persist approved operations, reports, ledgers, pending revision drafts and their input snapshots. Setup, revision-diff, ExampleGuide, ReportTime, RouteMap and their existing tests were inspected before changes.

## Restoration

Browser storage holds only an operation reference and pending job reference, keyed by issuer/client/subject. Every restore uses the existing authorized operation API. It restores the server snapshot, including history, ledger, approved revision and pending draft. Explicit loading/error states prevent the empty-deliveries flash; errors offer Retry and Open saved runs. Session expiry/sign-out clears references and operational state; request cancellation and account-keyed remounts ignore stale results. Completed job snapshots cannot overwrite newer reports.

If browser storage is unavailable, automatic reference restoration is unavailable; saved runs remain accessible through the API. A local server restart loses an in-flight job, but retains the last saved operation and completed draft. An unknown pending-job status is reported explicitly. No draft is simulated or automatically approved.

## Revision metrics and diagnostics

- Previously reported delivered: `revision_accounting.reported_delivered_litres`.
- Newly scheduled: `revision_accounting.additional_scheduled_litres`.
- Remaining unmet demand: `revision_accounting.remaining_unmet_requested_litres`.
- Depot water not scheduled: draft `stock_ledger.depot_litres` minus newly scheduled. Reported deliveries are already removed from depot stock; stranded water is excluded. No second subtraction of deliveries occurs.

Capacity is described as a verified ceiling only when the validated draft's available vehicles are unused, at the depot, not failed or returned, each route uses its vehicle's entire capacity, route loads equal stop totals, and aggregate capacity equals additional scheduled water. Other results explicitly state that a verified limiting-constraint explanation is unavailable. This is a narrow diagnostic, not a proof of global optimality.

The synthetic browser run recorded a 5,000 L load, 700 L cumulative delivery, vehicle failure and 4,300 L physical recovery. Its ledger then contained 11,300 L at the depot. Two eligible unused vehicles of 4,000 L and 3,000 L capacity scheduled 7,000 L; the draft displayed 700 L previously delivered, 8,400 L unmet and 4,300 L unscheduled depot water. Draft review and approval remain separate.

## Interface changes

Central navy/blue/teal tokens, stronger muted text, amber reductions with signed quantities and text labels, compact guide/account/footer, expandable provenance, one demo notice, labelled scrollable tables and responsive navigation reduce clutter. The mobile drawer manages focus, Escape, keyboard trapping and background interaction. Setup measures its action bar and reserves its actual height plus 16 px. Report actions select the same type handler as manual selection and focus the required field. Success resets event inputs; failures retain them; duplicate submissions are guarded.

Breakdown guidance adds ten minutes in absolute time and converts through the existing IST helpers, including midnight rollover. Validation rejects earlier events and preserves valid equal timestamps. Report-specific help explains cumulative deliveries, stranded water, recovery and signed stock adjustments.

Map states are unloaded/loading/loaded/failed. Fit route appears only after tile readiness. Retry and stop/directions fallback survive tile failures. Dashed connections mean stop order, not verified road navigation.
